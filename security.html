Security and responsible disclosure

Last reviewed 6 November 2026. This page describes the current security model and how to report a problem. It is not a certification, a penetration-test report or a promise that no vulnerability exists.

Report a security issue

Email security@popuploom.com with the subject “PopupLoom security report”. This is the monitored security contact for the project.

Please include:

  • the affected URL, endpoint or widget id;
  • a short description of the issue and its impact;
  • reproduction steps or a minimal proof of concept;
  • the date and time of your test;
  • whether any personal data was accessed, and if so, what you did with it.

Do not include other people's personal data, passwords, session tokens or live payment details. If you need to demonstrate a data exposure, use a test account you control and redact the evidence.

Response targets (best effort, not a legal guarantee): acknowledge a complete report within 3 business days; provide an initial assessment within 10 business days; agree a disclosure timeline after the issue is validated. Complex reports or reports requiring account-owner cooperation may take longer.

Scope

In scope:

  • https://popuploom.com/ and its public pages;
  • the authentication and account APIs;
  • widget configuration, view and submission APIs;
  • the embedded popuploom.js runtime on a test page you control;
  • server-side webhook configuration and delivery;
  • the password-reset flow.

Out of scope:

  • denial-of-service or load testing against production;
  • social engineering of the operator or users;
  • reports that only show a missing security header without a demonstrated impact;
  • third-party services (Cloudflare, Google, Resend) outside PopupLoom's configuration;
  • testing against a customer's website or popup without that owner's permission.

Safe testing rules

  • Use accounts and websites you own or have explicit permission to test.
  • Do not access, modify, delete or exfiltrate another user's popups or leads.
  • Stop as soon as you have enough evidence to demonstrate the issue.
  • Do not run automated scanners at a rate that degrades the service.
  • Do not publicly disclose an unresolved issue before a fix or an agreed timeline.

PopupLoom will not pursue legal action for good-faith research that follows these rules, but this page is not a legal safe-harbour statement and does not override applicable law. Consult your own legal advice if you need a formal agreement.

How PopupLoom protects accounts

  • Passwords are stored as one-way hashes, never plaintext. The Worker uses PBKDF2-SHA256; the Express runtime uses bcrypt and upgrades legacy hashes on login.
  • Session tokens are signed server-side, expire, and can be revoked. Changing a password or resetting it invalidates existing sessions through a token version.
  • Login and password-reset responses are deliberately generic so they do not confirm whether an email address has an account.
  • Password-reset tokens are random, single-use, expire after 30 minutes and are stored only as a SHA-256 hash. The raw token stays in the email link fragment and is removed from the address bar.
  • Private API routes require a bearer token and reject untrusted browser origins.
  • Rate limits are applied to login, registration, password reset, lead submission, view events and general API traffic.
  • PopupLoom takes no payments and asks for no card details. Google sign-in uses Google Identity Services; there is no separate "Google verification" page on this site.

How PopupLoom protects popups and leads

  • Widget and lead queries are scoped to the signed-in owner. Changing another user's widget id does not grant access.
  • Widget ids are generated server-side from 96 random bits; a client cannot choose or reclaim an id.
  • Popup configuration is validated for size, depth and unsafe keys before it is stored.
  • The embed escapes text, attributes and URLs before rendering. Video embeds are limited to HTTPS YouTube/Vimeo hosts and run in a sandboxed iframe.
  • The current runtime does not write submitted form responses to the customer site's browser storage. It removes legacy pfsubs.* entries when it loads.
  • Server-side webhook URLs and signing secrets are stored separately from public widget configuration and are available only to the signed-in owner.
  • Webhook deliveries are signed with HMAC-SHA256, use a timestamp, do not follow redirects, and reject private or local destinations. Hostnames are resolved and rechecked before delivery.
  • CSV exports escape spreadsheet formulas and preserve quotes and Unicode.

Infrastructure and data

  • The public site and API run on Cloudflare Workers with D1 storage. Traffic uses HTTPS; HTML responses include CSP, HSTS, framing, MIME-sniffing and referrer protections.
  • Advertising is live only on public content pages. The AdSense integration is fail-closed: it loads nothing unless the account is approved, a valid slot exists, and the Google Privacy & messaging CMP is configured. The editor, account pages, lead inbox, password-reset and verification pages, and customer embeds are excluded.
  • Password-reset and signup-verification email is sent through Resend. The API key is a server-side secret and is never sent to a browser.
  • Popup owners are the controllers of the lead data they collect. See the privacy and data handling page for storage, browser storage, webhooks and deletion.

Incident response

Security reports and suspected incidents are triaged by severity. The response sequence is: contain the affected service, preserve evidence, identify the root cause, remove unauthorised access or code, rotate affected credentials, restore trusted service, and notify affected users where required. A public post-mortem is published when it would not expose personal data or create additional risk.

This is a small independent project; response times vary and are not guaranteed. There is no 24/7 security operations centre.

What this page does not claim

  • It does not claim ISO 27001, SOC 2, PCI DSS or any other certification.
  • It does not claim that an independent penetration test has been completed.
  • It does not claim that every third-party scanner will agree with this page.
  • It does not guarantee uptime, data recovery or a particular response time.

Security is an ongoing process. The repository's security.txt records the current contact and expiry, and this page is updated when the model changes.

If you are a security vendor

If a PopupLoom URL is classified incorrectly, email the same address with the vendor name, the exact warning text, the detected URL and the date. Include any public report URL. We will review the evidence, fix confirmed issues and request re-evaluation through the provider's official channel. We do not ask vendors to remove accurate warnings.
